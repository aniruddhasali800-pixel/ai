02What the product does

Sizzle is the operating system for one restaurant floor. Six kinds of person touch it, and the point of the build is that they are all looking at the same rows in the same database at the same second.

WhoWhere they liveWhat they can do
Guest at a table/t/<tableToken> from a printed sticker, then /s/<publicToken>Read the menu, seat themself, punch orders, watch each ticket move, raise a call (water, cutlery, bill), pay a UPI charge, see the GST bill
Guest with the installed app/eat/<slug>, /track/<token>Pickup and delivery orders, live ticket tracking, checkout
Waiter/floor — floor map, new order, table ticketSeat and open tables, punch orders for any table, run food, ask the counter for a bill, clear a table, answer “where is my order”
Kitchen/kds — four-column passAccept, start, mark ready — per station, nothing else
Cashier / counter/pos — bills and the request queueIssue bills, take cash and online payments, settle and refund, confirm a table clear
Owner / manager/app — dashboard, orders, tables, menu, bookings, inventory, staff, reports, delivery, audit, settingsEverything operational; only the owner writes restaurant settings and integrations

One service period, end to end

  1. A guest scans the sticker on table M3. GET /api/public/menu/:tableToken returns the menu plus a session for the table; the guest orders two dishes. POST /api/public/session/:token/orders creates an Order with source: DINE_IN_QR.
  2. The order row is priced on the server (pricing.service.ts), saved, and broadcast: order.created to kitchen:<rid> and restaurant:<rid>, a Notification to the waiter room, and the table flips to ORDERING.
  3. The kitchen taps Accept, then Start, then Ready on /kds. Each is PATCH /api/kitchen/orders/:id/status, guarded by kitchen:operate and by ORDER_TRANSITIONS. Recipe stock is deducted once, at the first PREPARING.
  4. Any waiter sees FOOD_READY on the floor map, walks it out and marks Served — orders:status is held by waiters, so this is allowed.
  5. The guest asks for the bill. That is a CustomerRequest of type BILL with raisedByUserId set. The counter accepts it, which issues one Bill for the table’s unbilled orders; the bill and its UPI QR go back to the waiter who asked, not to whoever happens to hold the table.
  6. Cash is tendered at the table, so the waiter raises CASH_PAYMENT; the counter records the payment, and only then may the table be cleared. TABLE_CLEAR exists so the floor cannot silently free a seat with money still on it.
Why the whole thing is realtime. Every one of those steps is somebody else’s screen. A toast that never appears is a dish that never leaves the pass, so notifications and socket invalidations are treated as function, not polish.

Why these choices, in one line each

  • Express + Mongoose over a framework. The API is 18 small routers; a framework would buy structure this codebase already gets from src/modules/<feature>/.
  • MongoDB with an embedded server. A demo that boots with npm run dev and no account is worth more than a correct one that needs Atlas first. MONGODB_URI switches to a real cluster when it is set.
  • A hand-rolled query cache (src/lib/query.ts) instead of a data library: the cache is keyed by URL and invalidated by socket events, which is the whole requirement.
  • Hand-drawn SVG charts (src/components/charts.tsx) instead of a charting dependency.

Because the browser reaches both halves from the address it is standing on, the client is built with VITE_API_URL= empty: API_ROOT is '', calls go to relative /api, and no CORS hop exists for its own traffic. The old host ai-ecru-kappa-14.vercel.app is the same Vercel project, so it gets the same rewrites and keeps working — that matters because stickers were printed against it.

One caveat worth knowing. Vercel cannot upgrade a WebSocket through a rewrite, so Socket.IO settles on HTTP long polling on that domain. The client asks for ['websocket','polling'], so a direct Render or laptop connection still upgrades. Nothing in the code depends on the transport.

The life of a request

  1. src/server.ts creates the app, connects Mongo, starts the scheduler and attaches Socket.IO to the HTTP server.
  2. createApp() in src/app.ts: webhooks are mounted before express.json() because a signature must be verified against the raw body; then helmet, cors, morgan, JSON, the /uploads static mount, Cache-Control: no-store on /api, the routers, then the SPA fallback and the error handler last.
  3. requireAuth (middleware/auth.ts) verifies the access JWT, re-reads the user row and puts {userId, restaurantId, role, name} on req.auth. Scope always comes from the database, never from the token’s claims alone.
  4. requirePermission('…') or requireRole(…) (middleware/rbac.ts) resolves the role against ROLE_PERMISSIONS at request time, so editing the grid needs no reseed.
  5. validate({ body }) parses a Zod schema; anything unknown is rejected before a handler runs.
  6. The handler is wrapped in asyncHandler, so a rejected promise becomes ApiError and the error middleware answers { error: { code, message } } with the right status.
  7. Business rules live in src/services/*, not in the handler. A write that matters also emits: emit.ts pushes to rooms and notification.service.ts persists a Notification row so a screen that was closed still shows it later.

How a change reaches every other screen

  service writes Mongo  ->  emit.toKitchen(rid, 'order.ready', payload)
                        ->  notify({ recipientId })  ==  Notification row + 'notification:new' to user:<uid>
  browser: socket.ts receives -> useRealtimeShell maps the event to invalidate('floor'), invalidate('kds')
         -> lib/query.ts bumps a generation -> useQuery refetches -> component re-renders
         -> toast in Toaster + bell badge for the human

That indirection is deliberate: a socket event says “something changed”, the data itself still comes from the same REST endpoint the screen loaded at boot. A missed event costs a stale row until the next 20-second refresh window; it cannot corrupt anything.

06Backend anatomy

Boot sequence (src/server.ts)

  1. Parse and validate the environment. A bad variable stops the process with the field errors printed.
  2. In production, refuse to start on a missing MONGODB_URI or a development-default token secret.
  3. Connect Mongoose. With no URI, start mongodb-memory-server on .data/mongo (tests use .data/mongo-test) and connect to it. Only one process may hold that directory — see §19.
  4. If AUTO_SEED is not false and there are zero restaurants, load the demo tenant.
  5. Bind HTTP, mount Socket.IO on the same server, start the scheduler.

Middleware, in the order it matters

  • auth.ts — bearer only; 401 messages are explicit (“Please sign in to continue”, “Session expired, please sign in again”).
  • rbac.ts — requirePermission, requireRole; a mismatch is 403 with the permission named.
  • validate.ts — Zod schema against body/query/params; the parsed value replaces the raw one.
  • rateLimit.ts — separate limiters for auth attempts, general public traffic and public writes.
  • upload.ts — multer disk storage, jpeg/png/webp/gif, 5 MB cap, filename <timestamp>-<token6><ext>.
  • error.ts — ApiError to status + {error:{code,message}}; anything unexpected logs and answers 500 without leaking internals.

Where the data physically lives

  • Nothing set: mongodb-memory-server runs a real mongod against backend/.data/mongo. It survives restarts locally, which is why a reseed is a deliberate act (npm run seed:fresh, or deleting that folder).
  • MONGODB_URI set: a real cluster (Atlas M0 in the README). Then npm run seed also works from a Render shell, because both containers see the same database.
  • Uploaded photos: backend/uploads on the container’s disk. A redeploy wipes them — object storage is the fix for a real install; committed art under frontend/public survives.
  • Every token and QR in the database is regenerated by a reseed. Codes printed before a rebuild point at tokens that no longer exist.

09State machines

Transitions are declared once, in src/types/constants.ts, and enforced in the service — a client cannot jump a row by sending a status it likes.

Order

PLACED ──> ACCEPTED ──> PREPARING ──> READY ──> SERVED ──> COMPLETED
   │            │             │            │
   └────────────┴─────────────┴──────────────> CANCELLED      READY may also go straight to COMPLETED
Target statusRoles allowed to move an order into it (TRANSITION_ROLES)
ACCEPTED, PREPARING, READYKITCHEN, MANAGER, OWNER
SERVEDadds WAITER and CASHIER
COMPLETEDCASHIER, WAITER, MANAGER, OWNER
CANCELLEDCASHIER, MANAGER, OWNER

A settlement is a system transition: transitionOrder(…, { system: true }) skips the role check and may complete an order from any reachable state, which is how paying a bill finishes the tickets behind it.

Table, session, booking

  • Table AVAILABLE → RESERVED → OCCUPIED → ORDERING → FOOD_READY → BILL_REQUESTED → PAYMENT_PENDING → CLEANING → AVAILABLE. A clear that still has money on it stops at PAYMENT_PENDING.
  • Session OPEN → BILL_REQUESTED → PAYMENT_PENDING → CLOSED. The session id is the key the punch queue uses (§10).
  • Booking PENDING → CONFIRMED → ARRIVED → SEATED → COMPLETED, with CANCELLED and NO_SHOW reachable from the first three.

Side effects that are part of the machine

  • First move to PREPARING deducts the recipe once, and writes InventoryTransaction rows.
  • READY notifies the waiter who holds the table and the waiter room, so a colleague can run it.
  • Every transition appends to statusHistory[], which is what /orders/:id/timeline renders.
  • Stock and status changes are audited through audit.service.ts.

10The two floor rules

Both of these came from real failures on the floor and both are covered by tests in backend/tests/cashflow.test.ts. Do not “simplify” them away.

Rule 1 — one fire per table

A punch that arrives while the table’s current order is still PLACED or ACCEPTED — that is, before the kitchen has begun cooking — is merged into that order instead of creating a second ticket. The response carries { merged: true } so the caller can say “added to the running order” rather than showing a new ticket number. Once the order is PREPARING or later, the next punch is a genuine second round with its own ticket.

order.service.ts
  createOrder(input)                  // entry point for every source
    └─ key = String(input.tableSessionId)
       tail = (punchQueues.get(key) ?? Promise.resolve()).then(() => placeOrder(input))
       punchQueues.set(key, settled)  // the next punch on this table waits for this one
       ...cleanup when settled
  placeOrder(input)                   // the merge check happens inside the queue

The queue exists because two phones can punch the same table within a few milliseconds of each other, and both would read “no open order” before either wrote. Serialising per session closes that window without refusing anyone. MERGED_SOURCES limits the merge to DINE_IN_QR and DINE_IN_WAITER: a guest tap and a waiter punch land on the same ticket, which is exactly the case that produced two bills for one dish.

Known limit. punchQueues is an in-process Map. It is correct on one API instance — which is how this project deploys — and would need a database-level guard (a unique partial index on “the table’s open unbilled fire”) to be correct across replicas.

Rule 2 — the name on a table is a label, not a lock

Every waiter works every table. takeTableForWaiter() writes the seating waiter’s name only while assignedWaiterId is still null, and the write is conditional so two phones tapping the same free table settle on one name instead of overwriting each other. Nothing downstream refuses a colleague: any waiter can add items, serve, bill and clear a table they are not named on. The floor shows “with Sneha Patil” as information, and NewOrder says in words that anything punched there lands on the same ticket, so the party is billed once.

Related decisions: a cleared table loses its waiter name (tables.routes.ts sets assignedWaiterId = null), and the seed leaves free tables unnamed — a demo floor with a name printed on every seat makes “take this table” impossible to reach and looks like the ghost shift is working.

Where a bill goes when it is asked for

A BILL or TABLE_CLEAR request records raisedByUserId. When the counter accepts it and issues the bill, the notification goes to the raiser and the name on the table, deduplicated; if neither resolves it goes to the waiter room. This is why a waiter who raised the call can open the bill and show the guest the QR even when the table belongs to someone else.

11Money

Pricing is computed on the server, always

services/pricing.service.ts recomputes every line from the database row: unit price from Product, add-on prices, per-item taxPercent or the restaurant default, quantity, line total, then subtotal, tax, service charge, discount, and roundOff to the nearest rupee. A client-sent total is ignored. tests/pricing.test.ts exists precisely to keep that true.

Bill

  • Number INV-<YYYYMMDD>-<NNNN> from the atomic Counter; one bill gathers the table’s unbilled orders and stamps billId on each.
  • taxBreakup[] splits CGST and SGST for a GST bill the guest can read at /bill/<billToken>.
  • publicToken makes the bill readable without a login — that is the QR the waiter shows.
  • printCount and lastPrintedAt exist because a printed bill is a legal artefact.

UPI and payments

  • upi.service.ts builds upi://pay?pa=&pn=&am=&cu=INR&tn= from the restaurant’s payment.upiId and renders a QR data-URL. No UPI handle configured means no charge is offered, not a broken link.
  • integrations/payments.ts has two providers: a mock (which returns a checkoutUrl to /pay/mock and needs an explicit POST /payments/:id/simulate or a verified webhook to mark money in) and Razorpay wiring behind optional keys. A payment is never marked paid by a client assertion.
  • Cash at a table is a two-step dance on purpose: the waiter raises CASH_PAYMENT with the tendered amount, the counter records it (…/collect, …/settle), and only then may the table be freed. Waiters hold billing:write and payments:read but never payments:write.
  • Refunds are a separate permission (payments:refund) and a separate status, including PARTIALLY_REFUNDED.

12Auth, sessions and permissions

Tokens

  • Access JWT { sub, rid, role, name }, TTL ACCESS_TOKEN_TTL (15 minutes). Sent as Authorization: Bearer. The middleware re-reads the user row, so a suspension or role change takes effect on the next request.
  • Refresh JWT { sub, v }, TTL REFRESH_TOKEN_TTL_DAYS (7 days). Only the bcrypt hash of v is stored, in User.refreshTokens[].
  • Per-device sessions. Each sign-in appends a slot; the list is capped at 5 and the oldest is evicted. Refreshing rotates only the caller’s slot, so the counter tablet stays signed in while a phone refreshes. POST /auth/logout with a refreshToken ends that device; without one it ends all of them. Resetting a staff password clears the whole list.
  • The client’s 401 interceptor refreshes in a single flight and replays the original request once (_retry).

OTP sign-in

Floor roles only — WAITER, KITCHEN, CASHIER — because those are the accounts a hired person may not have a password for yet. Six digits, five-minute TTL, five attempts, three requests per fifteen minutes, stored as a bcrypt hash in LoginCode with a TTL index that garbage collects it. There is no SMS gateway, so outside production deliver() logs the code and returns it; that is a demo door, and it is why owner and manager are excluded.

The permission grid (ROLE_PERMISSIONS)

RolePermissions

The client keeps a mirrored copy in frontend/src/store/auth.ts as PERMISSIONS plus can(role, permission), and it is used only to decide what to render. The server checks again on every route; hiding a button is not a security boundary.

Demo master password

DEMO_MASTER_PASSWORD (Sizzle@Master1) opens any active account — but only in the tenant whose slug is saffron-and-smoke, and only while NODE_ENV is not production, where the value arrives empty. A restaurant that onboarded itself through /register is a different tenant and the master gets nowhere near it. Suspended accounts are refused before the master is compared, and a failure caused by the master is indistinguishable in wording from any wrong password.

13Realtime contract

Socket.IO on /socket.io, same HTTP server. The handshake takes auth.token; a valid JWT joins the rooms its role implies, and an invalid or absent token is not rejected — it becomes a guest socket that may only join by public token.

RoomWho is in it
restaurant:<rid>Every staff socket of that tenant
kitchen:<rid>, cashier:<rid>By role, for the pass and the counter
waiter:<uid>, user:<uid>Named delivery to one person’s devices
session:<publicToken>, order:<trackingToken>A guest’s own table or ticket, joined only after the server validates the token

Client → server: join:session, join:order, leave:session, leave:order, each with an { ok } acknowledgement. The client keeps its own set of joined tokens and replays them on every connect, because a reconnect silently loses room membership.

Data layer

  • lib/api.ts — API_ROOT from VITE_API_URL, empty meaning same host. Attaches the bearer token unless a caller already set one, refreshes once on a 401 for non-auth routes, and normalises errors through errMsg() which reads data.error.message. mediaUrl() turns a stored /uploads/… path into something loadable from another origin.
  • lib/query.ts — a Map keyed by a string, peek / write / patch / invalidate / invalidateMany, and useQuery(key, url) with a 20-second freshness window plus a generation counter so an invalidation from a socket refetches the mounted screen. patch is what makes an optimistic update possible without a library.
  • lib/socket.ts — the singleton socket, a generation number that is bumped whenever the socket object is replaced (subscribers read it through useSyncExternalStore, so a token refresh cannot leave every component bound to a dead socket), the reconnect room replay, and the failed-handshake counter that mints a fresh access token after two consecutive failures.
  • store/auth.ts — persisted under sizzle.auth: user, restaurant, both tokens, ready; login, loginWithCode, register, logout, bootstrap, and the mirrored permission map.
  • store/notifications.ts and store/toasts.ts — in-memory; the bell hydrates from the API, toasts expire on a timer.
  • hooks/useRealtimeShell.ts — mounted by all four staff layouts; maps each socket event to the query keys it invalidates and to a role-targeted toast. This is the file to edit when a new event needs to reach a screen.

UI system

Tailwind v4 with no config file: the design tokens live in src/index.css under @theme — display font Bricolage Grotesque, body Inter, and the palette scales ink (warm charcoal), ember (brand orange), saffron, leaf. Shared classes .card, .field, .label and the sizzle-in, sizzle-pulse, sizzle-slide keyframes are defined there. Primitives are in components/ui.tsx (Button, LinkButton, Card, Modal, Drawer, Field, Tabs, StatTile, VegDot, DishThumb, Toggle, SegmentedControl, Spinner), with DataTable, QrScanner, UpiQr, Toaster, NotificationBell, ImagePicker, OperationsAppModal and charts.tsx above them. Status-to-colour copy is centralised in lib/statusMaps.ts so “READY” reads the same on the pass and the floor.

Types in lib/types.ts are a hand-maintained mirror of the backend shapes — not generated. When a field changes on a model, both files must move together; nothing will tell you.

Deploy

  1. Render — render.yaml is a Blueprint (New → Blueprint at this repository). Root directory backend, build npm install && npm run build, start node dist/server.js, health check /api/health. Only MONGODB_URI is left to fill in.
  2. Vercel — project root frontend, so frontend/vercel.json is read. The four rewrites in §04 must stay ahead of the SPA fallback; a catch-all first answers an API call with index.html, and an unknown top-level key in that file fails the build outright.
  3. Push to main deploys both. Expect Render to take a few minutes and to wipe and reseed the embedded database on the way up.
Two deployment facts that surprise people. A redeploy resets the demo tenant, so every QR token, session token and JWT changes — codes printed from the previous instance stop resolving. And the service’s NODE_ENV is not production on Render even though render.yaml sets it, so anything that must apply to the deployment has to key on RENDER_EXTERNAL_URL being present, not on env.isProd.

19Deliberate mocks, limits and debts

Mocked on purpose

  • Payments. A card or UPI settlement needs the explicit POST /payments/:id/simulate the counter makes, or a signed webhook. Money is only ever marked in by an event, never by a client saying so.
  • Delivery partners. Swiggy, Zomato and the website channel run through adapters that simulate unless API keys are present; POST /integrations/simulate/:provider exists so the floor can be rehearsed.
  • SMS. No gateway, so the OTP code is logged and returned outside production — which is why floor roles only may use it.

Structural limits

  • Single process. The punch queue and the scheduler’s interval are in-memory. Correct on one instance; a second replica needs database-level guards and a distributed lock.
  • Embedded database on the free tier. Every deploy wipes and reseeds. Real use means MONGODB_URI plus object storage for uploads.
  • Types are mirrored by hand between backend/src/models and frontend/src/lib/types.ts, and permissions are duplicated between constants.ts and store/auth.ts. Nothing enforces they agree.
  • Rate limits are in-memory, so they reset with the process and do not span replicas.
  • WebSocket upgrade is lost behind the Vercel rewrite; realtime on that domain rides long polling.

Debts worth scheduling

  • @clerk/express, @clerk/clerk-react and @clerk/react are declared in both package.json files and imported nowhere; the two files left behind (backend/src/modules/auth/clerk.webhook.ts, frontend/src/components/ClerkAuthBridge.tsx) are one-line stubs saying “no longer used”. Auth is the custom JWT scheme in §12. Remove all of it.
  • onRealtimeAuthFailure() is exported from lib/socket.ts but no module calls it, so the socket’s self-healing token refresh never fires — the HTTP layer’s own 401 path is what keeps sessions alive today. Wire it or delete it.
  • Realtime events are untyped on the client: the names in emit.ts and the strings in useRealtimeShell.ts agree only by discipline.
  • Menu photos have no checksum or dedupe; re-uploading the same dish art accumulates files.
